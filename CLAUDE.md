# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Flask app that monitors network uptime for Location A's wireless network (and now other **locations** too). It tracks a list of access points (APs) and switches by ICMP ping, records results to a database, posts Slack alerts when device states change, and serves a live D3.js topology map (switches with their child APs arranged radially) that supports drag-to-reposition, manual checks, per-device notes, and adding/deleting devices from the UI.

**Pinging is split into two halves** because the production app runs on Heroku, which can't reach the the private device addresses (`192.0.2.x` / `198.51.100.x`):
- **The web app** (this repo's `app/`) runs on Heroku — dashboard, API, database, Slack alerting. It does **not** ping anything itself in production.
- **One or more remote agents** (`agent/ping_agent.py`, stdlib-only, see `agent/README.md`) run on a network that can reach the devices, pull the target list from the app, ping locally, and POST results to `/api/agent/report`. Production runs a **single Windows Server agent as `SITE=all`** (master `AGENT_TOKEN`), which pings every location and is what the dashboard's **Download agent** button hands out; the code still supports a per-site agent (`SITE=<key>`, per-site token) if ever needed. Running two agents against the same devices is safe (see the confirm-down debounce below) — e.g. two Windows boxes during a migration. **Windows caveat:** `ping` exits 0 even for unreachable hosts, so the agent requires a real echo reply (`TTL=`) to count a host up — don't "simplify" that back to a bare exit-code check.

## Commands

```bash
pip install -r requirements.txt   # flask, pyyaml, gunicorn, psycopg (Postgres), openpyxl (xlsx export), Authlib+requests (Okta SSO)
python run.py                     # local dev web server (no pinging by default)
```

No tests, linter, or build step exist. In production gunicorn runs `app:create_app()` (see `Procfile`). Pinging real hosts requires being on the device network; off-network everything reads `down`/`unknown`. The in-process scheduler is **off by default** — set `ENABLE_LOCAL_PING=1` to run the pinger inside this app (only useful when the app itself is on the device network); otherwise pings come from the remote agent.

## Architecture

**App factory.** `app/__init__.py:create_app()` loads `settings.yaml`, inits the DB, seeds the device list if empty (see below), loads devices/switches from the DB into `app.config`, registers the blueprint, and — only if `ENABLE_LOCAL_PING=1` — starts the in-process ping scheduler. The scheduler (when enabled) runs in a **daemon thread** (`app/monitor.py`), a hand-rolled `threading.Event`-gated loop (no APScheduler/cron) that calls `check_all_devices` every `polling.interval_minutes`.

**Persistence is dual-dialect, chosen by `DATABASE_URL`** (`app/database.py`):
- **`DATABASE_URL` set** (Heroku/Neon) → Postgres via psycopg3 + a small `ConnectionPool` (**`min_size=0`** so it holds no idle connection and lets Neon's compute suspend; opens on demand). The legacy `postgres://` scheme is auto-normalized to `postgresql://`.
- **`DATABASE_URL` unset** → local SQLite at `data/monitoring.db` (auto-created), zero-setup offline dev. psycopg is imported lazily so offline devs needn't install it.
- The dialects differ in only a few places (placeholder token, upsert syntax, autoincrement, timestamp handling), handled by the `q()` helper and small `if _PG` branches — no ORM.
- **Timestamp caveat:** the frontend does `new Date(d.last_check + 'Z')`, expecting naive-UTC strings. `_norm()` converts any Postgres `datetime` back to a naive-UTC ISO string so the `+ 'Z'` logic works on both dialects. Keep that convention if adding time fields.

**The device list lives in the DB**, not YAML. The `nodes` table is the canonical list of switches and APs. On a fresh/empty DB, `create_app` **seeds it once** from `config/devices.yaml` (`db.seed_nodes_from_yaml`, guarded by `nodes_count() == 0`). Thereafter the DB is the source of truth and the UI's Add/Delete flows write straight to it (surviving Heroku dyno restarts — the bug the DB migration fixed). Editing `devices.yaml` after the table is populated has **no effect**; it's a frozen seed/backup that drifts from the live DB (re-seed an empty `nodes` table to re-import).

**Locations ("sites").** The app is multi-location: the `sites` table lists locations (seeded once from `settings.yaml`, then managed via the UI's location dropdown). Each `nodes` row has a `site`; nearly every request is scoped by `?site=<key>` (`_current_site`, `_site_nodes`), and each site alerts independently. The default site is the first row. Add/rename via `/api/sites`; per-site agent tokens are `AGENT_TOKEN_<KEY>` (the default site also accepts the plain `AGENT_TOKEN`). **Per-site Slack routing:** `SLACK_WEBHOOK_URL_<KEY>` (key upper-cased, dashes→underscores, loaded into `settings['slack']['webhooks']`) posts that location's outage/agent/reminder/deletion alerts to its own channel; the default site and **app-wide** alerts (DB-unwritable) fall back to the plain `SLACK_WEBHOOK_URL` (`notifier._webhook_for(slack_cfg, site)` resolves it; every alert fn takes a `site=<key>` arg). e.g. `SLACK_WEBHOOK_URL_LOCATION_B` → the org channel while the default site keeps `SLACK_WEBHOOK_URL`. **Location soft-delete:** `DELETE /api/sites/<key>` (admin-password-gated) does **not** delete immediately — it sets `sites.pending_delete_at = now + 24h`, posts a time-sensitive Slack notice, and leaves the location fully working. Viewing a pending location shows an in-app "undo" popup (`POST /api/sites/<key>/undo-delete`, login-only). The real deletion is a **lazy sweep** — `db.purge_due_site_deletions()` runs opportunistically from `/api/topology` and `/api/agent/report` (no dedicated scheduler), so it fires within a couple minutes of the deadline as long as the app gets traffic.

**Config YAML files** (`config/`):
- `settings.yaml` — polling cadence, Slack config, server host/port. The Slack `webhook_url` here is a **placeholder** (`…/YOUR/WEBHOOK/URL`, treated as unconfigured); the real webhook comes only from the `SLACK_WEBHOOK_URL` env var. Never commit a live webhook. `POLLING_INTERVAL_MINUTES` also overrides here.
- `devices.yaml` — the **seed** list of `switches:` and `devices:` (APs); canonical only until the DB is first seeded. Each AP has a `switch:` field naming its parent switch; switches have an optional `uplink:` naming their parent switch. Optional `x`/`y` bake in a layout baseline.
- `basemaps.yaml` — **optional** per-site aerial imagery: `tiles:` (path under `static/` to a generated tile pyramid) + `view:` (default visible lat/lng window). Read with `load_optional_yaml`, so a missing/malformed file degrades to "no imagery" instead of crashing `create_app` (unlike the two above, which use a bare `open()`). A site with no entry renders on the plain grid. See Aerial basemap below.

**Database tables** (auto-created by `init_db`): `ping_history` (**event log — one row per status *transition*, not per ping**), `device_states` (current status per IP — the **durable backing** for the in-memory status cache, written only on a transition; carries the `down_strikes` debounce counter), `app_downtime` (one row per detected monitoring outage — see below), `device_positions` (user-dragged x/y) + `device_positions_mobile` (the separate mobile layout) + `device_positions_geo` (lat/lng for the aerial basemap — **one per device, no desktop/mobile split**; see Aerial basemap below), `device_notes` (per-device free text), `pause_periods` (monitoring pause/resume intervals per IP), `scheduled_pauses` (pause windows: `start_at`/`end_at`/`device_ips` JSON/`status` scheduled|active|done/`mode`; plus `category`/`description`/`event_group_id` linking a pause to its Event), `nodes` (canonical device/switch list, each with a `site`), `sites` (locations, with `pending_delete_at` for soft-delete), `user_activity` (audit trail — one row per mutating request, scoped by `site`; see below), `maintenance_windows` (the **events** overlay — `[start_at, end_at)` per device with `category`/`note`(description)/`event_group_id`; re-labels outage time and excludes covered outages from the frequent count; see Events below), `app_flags` (key/value: the `ping_history_collapsed` / `ua_site_backfilled` migration flags and the per-site Slack "last message kind" — note the "check requested" flag, the `last_report` watermark, and `watchdog_alerted` are now **in-memory**, not here). All per-device tables are keyed by **IP**, not name. Schema changes are applied by small idempotent `_migrate_*` helpers in `init_db` (Postgres `ADD COLUMN IF NOT EXISTS` / SQLite `PRAGMA table_info` guards).

**Event model (why the DB doesn't grow with time).** `db.record_ping` appends to `ping_history` **only when a device's confirmed status changes** (up→down→up…), so a device that stays up writes nothing — storage scales with how often devices change state, not with time or device count. The read paths (`_device_transitions`, logs, `get_uptime_percent`) all derive intervals from these transition rows. A one-time startup migration (`_migrate_collapse_ping_history`, flag-guarded) collapses any legacy dense log down to transition rows. Three consequences to keep in mind when editing: (1) **uptime is time-weighted** (`get_uptime_percent` = fraction of *monitored* time up, excluding paused time), not a sample count; (2) **"app downtime" is stored as intervals, not samples** — `record_report(site)` (called once per `process_results` batch) refreshes the `last_report:<site>` watermark and writes an `app_downtime` interval **only when the gap since the last report exceeds `APP_GAP_SECONDS`** (the pipeline went quiet); `get_app_downtime_periods(site, since)` returns those intervals plus a synthesized ongoing one if the watermark is currently stale. (3) Don't reintroduce per-ping/per-cycle rows or infer app-downtime from `ping_history` gaps (it's sparse now).

**In-memory runtime state (the DB is barely touched in steady state).** To keep Neon's serverless compute able to auto-suspend, the **runtime source of truth lives in memory** (`app/database.py`), and the DB is written only on a *change* and read once at startup. `load_runtime_caches()` (called from `create_app`) loads `device_states` + `device_positions` into module-level dicts guarded by `_rt_lock`; thereafter: (1) **`record_ping` updates the in-memory `_states` cache UNCONDITIONALLY** (the cache is the live source of truth for the map + Slack and must never freeze) and write-throughs to `ping_history` + `device_states` on a **confirmed transition** — a stable "still up" ping writes nothing. The DB write is **best-effort**: if it fails (read-only DB, Neon cold-start blip) the in-memory status still updates, the transition stays **queued** (`_persisted_status` diverges from the live status) and is retried on each later report until it lands — no duplicate marker — and the failure is counted (`db_write_health()`) + logged loudly, never silently reverted. `record_report`/`mark_reminded` writes are likewise best-effort so a read-only DB can't 500 the report and skip Slack. (2) **`get_all_states` (the 30s topology poll) and `get_positions` serve from memory** — no DB read; (3) the **last-report watermark** (`_last_report`) and the manual **"check now" flag** (`_check_requested` for full sweeps + `_check_requested_ips` for targeted single-device checks, consumed by the agent's ~20s target poll) are in-memory, so neither the report nor the poll hits the DB; (4) `get_overdue_down` (the prolonged-outage reminder) reads memory; (5) the **watchdog** reads sites/watermark from memory and runs its `scheduled_pauses` sweep query only when an open pause has reached its next boundary (`pause_sweep_due()` — the cached `_open_pauses` flag + `_next_pause_boundary`), so even an active multi-day pause issues **no** per-tick query between its start and end; (6) the site-delete purge is throttled (`_PURGE_INTERVAL_SECONDS`), and the **frequent-outage counts recompute only on a fresh app load/refresh** (`topology?fresh=1`) — never on the 30s poll or on a state change; a state change / maintenance edit just marks the cache dirty (`invalidate_outage_cache()`), and the next fresh load rescans `ping_history` only if dirty. **Consequences when editing:** this assumes **ONE web process** (gunicorn `1 worker × 4 threads` share the cache; the RLock guards them) — scaling to >1 dyno/worker would diverge and needs a shared store. Positions are **write-through on Edit-Map save only**, so any path that changes a device's IP or deletes it must migrate/evict the cache (`update_node`, `delete_node`, `delete_site` already do). Across a restart, `down_strikes` resets, `last_check`/watermark are unknown until the next report (app-downtime spanning the restart isn't recorded, and a still-silent site may get one repeat Slack notice); `_persisted_status` is re-seeded from `device_states` so a queued (unwritten) transition that spans a restart is lost from history but the live status is re-established on the next report. Don't add a DB read/write on the per-ping or per-poll hot paths without a matching cache.

**State-change detection drives alerts.** `db.record_ping` returns a `changed` boolean. Both the local scheduler (`check_all_devices`) and the agent-report path (`process_results`) record results, and **only if any device changed** send a single batched Slack message listing all currently-down switches and APs (`notifier.send_slack_update`). So Slack is event-driven (on transitions), not every cycle. Recovery ("all clear") messages are gated by `slack.alert_on_recovery`. Slack is **outbound-only** (an Incoming Webhook) — the app never reads the channel, so messages/reactions/replies there do nothing.

**Always-on background thread (`monitor.start_watchdog(app)`, started in `create_app`, disable with `ENABLE_WATCHDOG=0`).** A single daemon thread that does three jobs — it's the only code that runs without an agent POSTing, so it needs a **non-sleeping dyno** (fine on Basic+; an Eco dyno would sleep right when you need it). All three read from memory in the common case, so a healthy quiet fleet's watchdog issues **no DB query** and Neon can stay suspended. **Adaptive cadence:** the tick is `WATCHDOG_CHECK_SECONDS` (default **8h**) normally, tightening to `WATCHDOG_NEAR_PAUSE_SECONDS` (default **30 min**) whenever a scheduled-pause boundary is within the base window (`_next_watchdog_interval` → `db.seconds_until_next_pause_boundary()`); the between-tick sleep is interruptible so `monitor.wake_watchdog()` (called by the pause create/cancel routes) re-evaluates the cadence immediately. **Consequence:** the agent-silence and DB-writable alerts are only *evaluated* on a tick, so on a quiet schedule they can lag up to the base tick (8h) even though their thresholds are shorter — acceptable here because pauses are scheduled ≥8h ahead (`SCHEDULED_PAUSE_MIN_LEAD`, enforced on create), but if you need faster silence detection, split those two checks onto their own faster timer:
- **Agent-silence alerts:** compares each site's `last_report:<site>` watermark (in-memory) to now and Slacks **once** when it goes stale (> `WATCHDOG_STALE_MINUTES`, default 30) and **once** when it recovers (per-site in-memory `_silence_alerted` flag makes both fire once; resets on restart).
- **DB-writable alerts (`check_db_writable`):** reads the in-memory `db_write_health()` counter and Slacks **once** (`send_db_unwritable_notice`) when transition writes have failed `DB_WRITE_FAIL_ALERT_THRESHOLD` (default 3) consecutive times — i.e. the DB is reachable but unwritable (read-only) while the map/alerts keep running live — and once on recovery (`send_db_writable_notice`). This is the safety net that turns the old *silent* write-failure freeze into a loud alert.
- **Scheduled-pause sweep (`apply_scheduled_pauses`):** flips devices' `enabled` flag at a window's boundaries — pause at `start_at`, resume at `end_at` (skipping any IP another active window still covers) — then reloads `app.config` nodes. **Boundary-gated:** it only runs its DB queries when `db.pause_sweep_due()` is true (an open pause has reached its cached next boundary `_next_pause_boundary`), so between a pause's start and end it does zero DB work. The create/cancel routes call `refresh_open_pauses()` so a runtime pause updates the flag+boundary immediately (not just at the next restart). Idempotent, so a restart across a boundary catches up on the next tick.

**Confirm-down debounce (multi-agent safety).** A device flips to `down` only after `down_confirm_checks` consecutive down observations (default 2; `settings.yaml monitoring.down_confirm_checks`, overridable per-deploy by the `DOWN_CONFIRM_CHECKS` env var); recovery to `up` is **immediate** (`up` wins on the first observation). This absorbs single-cycle blips and keeps two agents pinging the same device flap-free, but note two consequences: (1) an outage shorter than `down_confirm_checks` polls, or a device answering intermittently, may never be recorded; (2) because `up` wins immediately, one agent falsely reporting `up` masks another's `down` — set `DOWN_CONFIRM_CHECKS=1` when a single agent is running if you want every blip recorded.

**Display convention: "Name" vs "Device ID".** In the UI/logs/Slack a device is shown by its friendly **Name** (the `location` field), falling back to its unique **Device ID** (the `name` field) when no Name is set. `name` remains the unique key (switch/uplink association is by it); `location` is the human label. The frontend helper is `displayName(node)`; the server mirrors it when building log entries and Slack messages.

**Audit trail (User Activity).** An `after_request` hook (`_audit_log` in `routes.py`) writes one `user_activity` row per successful, user-initiated **mutating** request (POST/PUT/PATCH/DELETE), skipping read-only/agent/auth endpoints. `_audit_summary` builds a human line ("Paused monitoring for Pole Barn AP", "Marked an outage as maintenance on …"); `_device_label`/`_ap_label` resolve the friendly Name (+ "AP" suffix for access points), preferring a name/kind the route stashed in `g` (for deletes/edits where the node is gone by after-request time). The **actor** is the Okta uniqname (`preferred_username`, falling back to the email local part). Each row is tagged with `_current_site()` and `/api/user-activity` returns only the current location's rows (a one-time `_migrate_add_user_activity_site` backfilled pre-existing rows to the default site). The UI shows it in the **User Activity tab** of the logs view with multi-select category filters (added / deleted / changed_monitoring / changed_maintenance / other, color-dotted).

**Events (generalizes maintenance) + optional pause.** An **event** is a named-by-**category** (maintenance=blue | lightning=yellow | power_outage=red | scheduled_downtime=purple | other=grey) window `[start, end)` over one or more devices, with a free-text description (stored in `maintenance_windows.note`). The **end is optional** — blank end → an open-ended/ongoing event stored with a far-future sentinel (`OPEN_ENDED_ISO`, shown as "ongoing"). It's a pure **overlay** — nothing in `ping_history` changes — and **all categories exclude covered outages from the frequent-outage count** exactly like maintenance did (maintenance is now just one category). Storage: one `maintenance_windows` row per device sharing an `event_group_id` (legacy single-outage marks have `event_group_id` NULL), **each with its own `start_at`/`end_at`** so a device can be **resolved independently** — its window capped while the event stays open for others (see below). **Activity-log display is pure tagging, not relabeling:** `_tag_events`/`_overlapping_events` leave each outage/pause/unknown period with its own status ("offline"/"monitoring paused"/…) and attach an `events: [{event_group_id, category, description}]` list for every event window that overlaps *that device's* period (`_snap_window` 60s absorbs minute residue). The frontend renders a "part of an event" chip; the `maintenance` log-list is now always empty. The **frequent-outage exclusion** (`get_outage_counts`) is separate and unchanged — an outage **fully covered** by any-category event window is excluded, a partly-covered one still counts. **Two ways to add a device** (both in the shared device picker's two tabs): from the **Device list** → joins with the event's full window (`device_ips`/`add`); from the **Activity log** → joins with that log entry's OWN window (`log_devices`/`add_log` = `[{ip,start,end}]`, `_clean_log_devices` normalizes; a blank end = still-ongoing item → `OPEN_ENDED_ISO`), so it's **auto-resolved** at the entry's end. **Per-device resolve** (`POST /api/events/<group_id>/resolve-device` `{ip, end_date?, end_time?}` — Eastern, default now; or `{ip, reopen:true}`) caps one device's `end_at` via `db.set_event_device_end`, so its earlier activity stays tagged but later unrelated outages don't; the event's overall span is min(start)/max(end) across rows, so it reads "ongoing" until every device is resolved. `update_event_times` moves the END only for rows still at the group max (so resolving survives a later group time-edit); START/category/description apply to all rows and category is editable post-create (`db.update_event_category`). **Future vs past/ongoing are fully separate flows.** **`POST /api/events/schedule`** (the "Schedule event" button on the event log + the device panel) creates a **future** event: required future start (device-list picker only, no log items), monitoring choice **above** the devices, optional scheduled pause (8h lead). **`POST /api/events`** (the "Mark an event" button) marks a **past or ongoing** event and is past-tense by default: an "Is this event ongoing?" checkbox reveals a "which devices are still affected?" device-list picker (those become open-ended rows to resolve later) + an optional pause that applies to **those** devices; start/end are each hidden behind an "Add a start/end date/time?" checkbox; the main picker is **log-only** — ticking a log item adds THAT item's window (the device itself isn't added full-window). An ongoing affected device with no start given is anchored at `db.current_issue_start(ip)` (its current outage/pause start, else now). **Timing model (CPU-critical):** a **present** pause (`start ≤ now`) is applied **immediately and directly** (`set_device_pause` now) and its `scheduled_pauses` row is created already `status='active'` — the watchdog only resumes it at `end_at` (existing boundary-gated sweep, **no cadence change**); a **future** pause (`start > now`) keeps the **8h lead** rule and the watchdog activates it at `start_at`. The overlay + pause are linked by `event_group_id`. **Pause-end auto-resolves the event:** when a linked pause ends — the watchdog resuming at `end_at` (`apply_scheduled_pauses`) or an admin cancelling an **active** pause (`cancel_scheduled_pause`) — `db.end_event_open_devices(group_id, ips, end)` caps only that event's **still-open** rows for those devices, so an event kept "ongoing" solely by its monitoring pause(s) ends once the pause(s) end. Devices left open for another reason (a genuine ongoing outage tagged to the event) keep it ongoing, and with multiple pauses the event ends only when the last one ends. (Cancelling a *scheduled/future* pause does NOT touch its not-yet-ongoing event.) Times entered Eastern, stored UTC. Routes: `POST/GET /api/events`, `PATCH`/`DELETE /api/events/<group_id>`; the per-outage quick tag stays at `POST /api/devices/<ip>/maintenance` (now takes a `category`) + `PATCH`/`DELETE /api/maintenance/<id>`. Also: `POST /api/events/<group_id>/devices` (add/remove devices; used by the log's "add to existing event"), `POST /api/events/<group_id>/resolve-device` (per-device resolve/reopen), `POST /api/events/combine` (merge selected events, single marks, **and device pauses** — pauses aren't deleted, just spanned). UI: the logs modal's **"Event Logs"** tab (Happening now / Upcoming / Past) — click an event → detail view (with "Edit devices"); a grey **Edit** button (bottom-left) enters multi-select for **Combine**/**Delete**; device monitoring pauses (`pause_periods`) are listed alongside events; the device picker shows per-device status dots. The "Mark an event" form; a per-device "Mark an event" action; and the per-outage log-entry path (category picker, widenable window, optional "add other devices", "add to existing event").

**Frequent-outage detection.** `get_outage_counts` counts each device's outages over the last `OUTAGE_WINDOW_DAYS` (15), excluding outages fully covered by an **event** window of any category; `_frequent_set` flags devices above `max(FREQUENT_MIN_OUTAGES, mean + 1 std-dev)` of the fleet. That count is a 30-day `ping_history` scan — the only DB read the topology endpoint would need — so it's recomputed **only on a fresh app load/refresh**: the browser's first fetch after a page load sends `topology?fresh=1` and `_outage_counts_cached(force=True)` rescans (but only if the cache is dirty); the recurring 30s poll sends no flag and **never scans**, serving the last value from memory. A device **state change** / **maintenance edit** just marks the cache dirty (`invalidate_outage_cache()`) — it does **not** scan — so with the app closed, or a flapping fleet, there are zero outage scans until a human opens/refreshes the dashboard. (Eager recompute-on-every-state-change was tried and reverted: on a flapping fleet it means a constant scan even with nobody watching.) Flagged devices render amber on the map and float to the top of the sidebar.

**Frontend is vanilla JS + D3** (`static/js/map.js`, no framework/bundler). It polls `/api/topology` every 30s, renders switches as rectangles with radially-placed AP circles, and links each AP to its parent switch (and switches to their uplink). The **"View logs" modal is tabbed** (site-wide): Device Logs / User Activity / Scheduled Pauses; per-device and per-switch logs reuse the Device Logs pane with the tab bar hidden. "Edit Map" mode drags nodes (dragging a switch moves its child APs **on the plain grid only**; over the aerial photo each device moves independently — see Aerial basemap) and persists positions **server-side** on Done via `POST /api/devices/<ip>/position` (or `…/geo-position` over an aerial basemap) — no localStorage overlay, so the layout is shared across browsers. Default positions (when none saved) come from `db.get_position` → `_yaml_pos` (the YAML baseline) → computed default (`_switch_default_pos` grid, `_ap_default_pos` radial). **Edit Map has two entry points** (admin), kept in sync by `reflectEditState()`: the on-map button (toggles Edit Map ⇄ Done) and a hamburger-menu item (`btn-edit-map-menu`). Bottom-left map controls: Edit Map + the aerial edit tools (**Set map area**, **Set auto-crop**, **Stack all** — shown only while editing over the photo, gated in `updateBasemapChrome` via `editingGeo = editMode && basemap.active`), **Select** (edit, either map), the photo toggle (**hidden while editing** — switching the photo mid-edit would swap coordinate spaces under the drag), a **Show/Hide labels** toggle, and Recenter (everyone). The **sidebar device list** puts **CURRENTLY DOWN first** (rendered only when outages exist), then the paused sections, frequent outages, then the kind sections (`updateSidebar`). In the four **special sections** (`down`/`paused`/`notif`/`frequent`, `GROUPED_SECTIONS`), a switch whose **every** connected device (its APs/'other' children) is in that same state collapses into one **"… & connected devices"** head row with a caret (`groupedItems`); the children render nested/indented beneath it and are hidden while the group is collapsed (`expandedGroups`, default collapsed, toggled by `window.toggleDeviceGroup`). The DOM stays **flat** (head + children are siblings, tagged `data-group`/`data-group-parent`) so `applyFilters` still iterates linearly — it hides collapsed-group children except when a search is active. The kind sections (switches/APs/others) are never grouped. On **mobile** (≤768px) the app **lands on the device list, not the map** (`body.view-list` set at load; the bottom Map⇄Devices toggle switches panes). The **header is the org Alumni Association branded** (the primary blue `#00274c` bar + the accent color `#ffcb05` rule, CSS vars `--um-blue`/`--um-maize`); it shows the logo from `static/img/um-alumni-logo.png` if present (the `<img>` self-removes on 404, so the file is optional). **Neutral palette:** every grey/black chrome color (`--bg`/`--surface`/`--surface2`/`--border`/`--text`/`--text-muted` in `:root`, plus the map's hardcoded grid `#1b2637` and connection-line `#6e88aa` in `map.js`) is a Michigan-Blue-tinted shade (hue ~212°) at its original lightness, so the whole UI reads as shades of the org blue while the contrast ladder is unchanged. Status colors (up green / down red / warn amber / paused purple / unknown grey) are deliberately left un-tinted.

**Aerial basemap (georeferenced photo under the map).** A location can show its devices on top of an aerial photo so an operator can tell which physical building a device is in. Configured per-site in `config/basemaps.yaml`; a site without an entry keeps the plain grid map unchanged (`location-b` has none). Key points:
- **Two coordinate spaces, one map.** With the photo on ("geo mode") **world space is level-0 image pixels** and each node's x/y is projected from its stored **lat/lng** at render time (`projectNodes` in `map.js`, before every `render`). With it off, the original logical x/y from `/api/topology` is used verbatim. The photo is a per-browser toggle (`localStorage` `apmon.basemap.on`), *not* a separate view — same nodes, links, sidebar, Edit Map. **`projectNodes` overwrites `x`/`y` in place**, so anything that leaves geo mode must **refetch** rather than re-render the cached `topology` (see `togglePhoto`) — re-rendering projected pixels in plain mode would show a broken layout and an Edit Map save would write image pixels into `device_positions`.
- **Positions are lat/lng, not pixels** (`device_positions_geo`, in-memory `_positions_geo` cache + `get_geo_positions`/`set_geo_position`, same write-through discipline as `device_positions`). That's deliberate: the imagery can be replaced, re-cropped, or swapped for live Leaflet tiles without moving a single device. `app/geo.py` (server) and the `toPx`/`fromPx` pair in `map.js` (client) are **the same Web Mercator formulas — keep them in step**. Positions have **no desktop/mobile split** (a building is in one place); Edit Map POSTs `{lat,lng}` to `/api/devices/<ip>/geo-position` in geo mode and the old `{x,y,layout}` otherwise.
- **Tiles, not one big JPEG.** `maps/build_tiles.py` slices a source raster into `static/basemap/<site>/v<n>/l<level>/<col>_<row>.jpg` (512 px, 4 levels) plus a `manifest.json` carrying the georeferencing **copied from the source `.bounds.json`**. The site is on **v2** — a wider ~3×-extent NAIP fetch (9167×8833 px @ 0.6 m/px, ~440 tiles / 18 MB) that shows the surrounding lake/woods/roads so the zoom-out view isn't mostly empty border (v1 was property-only). `drawTiles` joins only the visible tiles at `level = floor(log2(1/k))`, always keeping the coarsest level mounted so there's no blank flash. The `v<n>` segment is what makes the `immutable` cache header in `create_app` safe — **bump `--version` when regenerating**. The source rasters are gitignored; the tiles are committed (Heroku serves static from the slug, no CDN). **Regenerate with:** `fetch_imagery.py --source naip-usgs --bbox <xmin ymin xmax ymax> --res 0.6 --out <name>` → `build_tiles.py --in <name> --version <n>` → point `basemaps.yaml` `tiles:`/`view:` at the new manifest.
- **Node icons scale with the map (clamped).** In geo mode node groups get `scale(nodeScale())` where `nodeScale() = clamp(k, GEO_NODE_MIN_MUL, GEO_NODE_MAX_MUL) / k`, so the on-screen icon size (`k·nodeScale = clamp(k, MIN, MAX)`) tracks the imagery through the normal zoom range but is clamped to a readable band at both ends — a fully world-locked box would shrink to an unreadable sliver at the (now lower) zoom floor and swallow a whole building at the ceiling. All node kinds scale together (switch rects, AP circles, 'other' diamonds, and their text labels). Over the photo the switch box also shrinks to an AP-scale rounded box (`SW_W_GEO`/`SW_H_GEO`, set on the rect in `render`) since its label is hidden there and the full 120×40 box swamped the buildings; the plain grid keeps the full labelled box. Consequences: `swLinkPoints` must scale its box half-extents by `nodeScale()` (they're screen sizes compared against world deltas), switch-link endpoints are recomputed **on zoom** as well as on drag, and the `userSpaceOnUse` arrowhead markers are resized by `nodeScale()` (in both `render`'s first paint and `rescaleNodes`). `rescaleNodes` runs in plain mode too (where `nodeScale()` is 1) — otherwise a marker sized during a geo session stays oversized after the photo is switched off. **Plain grid map is untouched** (`nodeScale()` returns 1 there = world-unit geometry, the pre-existing look).
- **Both link kinds are hidden over the photo, and so are node labels.** In geo mode the device→switch dashed `line.ap-link` *and* the solid switch→uplink `line.sw-link` backbone are visual noise (that view is about physical location, not logical topology), so `render` sets their `display:none` while `basemap.active`. The always-on node **text labels** (`sw-label`/`sw-ip`/`ap-label`) are also hidden over the photo via CSS (`#map-svg.photo-on:not(.editing):not(.labels-on)`) — hovering a shape shows the existing status tooltip instead; labels reappear while editing so devices can be told apart, and a **"Show labels"** toggle (`#btn-labels`, everyone, shown only while the photo is on; per-browser `apmon.labels.on`, default off) adds `.labels-on` to force them on. On the plain grid everything is shown. `togglePhoto` refetches → `render` re-runs (which toggles the `photo-on` class), so visibility follows the photo state. **Offline (down) devices flash red** (`down-flash` keyframes — a pulsing red glow on the node group, plus the AP ring's `ap-pulse`) so an outage stands out even over the dimmed photo.
- **Recenter + marquee multi-select.** A **"Recenter"** control (`#btn-recenter`, everyone, always visible) just calls `fitView()` to return to the default opening view. In Edit Map a **"Select"** toggle (`#btn-select`) enters a marquee sub-mode (`selectMode`): a transparent `select-layer` rect below the nodes captures empty-space drags to draw a selection box (the zoom filter yields pointer-down drags to it while `selectMode`, keeping wheel-zoom), and nodes inside become the selection (`group-selected`; shift-drag adds). Dragging any selected node then moves the **whole set rigidly** (`makeNodeDrag` → `groupDrag`), while dragging an un-selected node clears the selection and does a single move. Selection is cleared on exit and never persists (only "Done" saves positions).
- **Edit Map placement is independent over the photo.** Dragging a switch moves **only** the switch in geo mode (`makeNodeDrag` skips the child-AP move when `basemap.active`) so each device can be pinned to its own building; on the plain grid the historical grouped move (a switch carries its whole AP cluster) is kept. A single unified `makeNodeDrag` handles switches, APs and 'other' nodes, single or as a selected group (see the marquee note above). A **"Stack all"** control (`#btn-gather`, shown only in Edit Map + geo mode) piles every device at one on-screen point (`gatherNodes` — transient until "Done" saves) so an operator can drag each out to its spot and read the shrinking pile as the un-placed set. `gatherNodes` must NOT call `render`/`projectNodes` (that would re-scatter the nodes back to their stored lat/lng).
- **Zoom/pan.** `translateExtent` clamps panning to the map area. The zoom **floor** (`geoFloorScale`) **CONTAINS** the map area with a margin (`GEO_FLOOR_MARGIN`) of empty background around it, so you can pull back and see the whole property at once with a dark border — below the cover scale d3 centres the map area (translateExtent stays the map area), so panning is simply disabled there rather than fighting the zoom. The **opening/fit** (`fitView`) frames the **site** (`propertyRectPx` from the manifest's `property_corners_latlng`, small margin, contained + clamped) rather than covering the whole much-wider image — otherwise the developed area opens buried in a corner of the surrounding lake/woods; it falls back to covering the map area if the manifest carries no property polygon. `fitView` centres within `availH`, but the zoom floor/ceiling are measured against **full** height because the mobile toggle bar overlays rather than shortens the map. The ceiling is `GEO_MAX_SCALE = 2` (1.0 = native image pixels ≈ 0.21 m/px — beyond ~2 there is no more detail, only upscaling). Meaningful context *beyond* the imagery (roads, neighbouring terrain) needs a **bigger source raster** — re-fetch + `--version` bump, don't upscale.
- **The visible area is refinable without a redeploy.** `basemaps.yaml`'s `view:` is the default (set to the **full image corners** from the manifest's `georef.image_corners_latlng`, so every committed pixel — including the ~50 m fetch margin past the property line — is reachable); an admin can drag a rectangle ("Set map area") which saves to `app_flags` as `basemap_view:<site>` and wins over the file (`PUT /api/basemap/view`, `{reset:true}` to clear). This exists so a future larger/sharper raster can be cropped to just the part that matters.
- **Admin-saved default opening view (per layout).** Distinct from the map area: the **"Set auto-crop"** button (Edit Map + geo mode) lets the admin **drag a rectangle**; the rectangle is saved as a lat/lng **`box`** (`{south,west,north,east}` via `fromPx`) — plus a centre + `k` for legacy fallback — as the opening view **for the current layout** (this replaced the older "Set default view" which saved the current pan/zoom — same storage + `fitView` path, just a rectangle-draw instead). **`fitView` re-derives the CONTAIN scale for the `box` in the current viewport every time** (`min(W/boxW, availH/boxH)`, clamped), so an odd/small window fits the more-constraining dimension and shows extra map on the other axis — the crop adapts to any window shape rather than baking in the zoom of the window it was drawn on. (A stored view with no `box` falls back to the legacy centre+`k`.) — a wide desktop framing suits a tall phone poorly, so desktop and mobile each get their own (`app_flags` `default_open_view:<site>` / `default_open_view_mobile:<site>`, served as `open_view` / `open_view_mobile` in `/api/basemap`, set via `PUT /api/basemap/open-view` with a `layout` field — admin-only, `{reset:true, layout}` to clear one). Set it once on a computer and once on a phone. On first load `fitView` picks the mobile view on phones (`mapLayout()==='mobile'`, falling back to the desktop one, then the property-frame) and centres that lat/lng at that `k` (clamped to the zoom limits) **instead of** the computed property-frame. It does **not** clamp panning (that's the map area) — it only sets the opening. Centre is version-robust (lat/lng); `k` is applied verbatim on the same imagery, so a re-fetch at a different resolution would need it re-set.
- **One-time seed.** `routes.seed_geo_positions(app)` (called from `create_app`, flag-guarded by `geo_seeded:<site>`) fits each site's existing logical layout into the map area (`geo.fit_layout_to_view`, uniform scale) so a location that gains a basemap opens with the familiar layout over the property instead of 100+ unplaced devices. It never re-runs (a reseed would undo real placement work) and never touches `device_positions`, so toggling the photo off returns to exactly the old map. Devices added later are placed by the frontend near their parent switch.
- **Config is served by its own endpoint** (`GET /api/basemap`, fetched on page load + site switch, never on the 30s poll); `/api/topology` gains only a memory-only `get_geo_positions` call, so the hot path stays DB-free. The manifest is read from disk once per site and cached (`_manifest_cache`).
- **Demo mode forces the photo off — toggle included** (an aerial view of the site identifies it as plainly as its name would). **Known gap:** `static` is in `_PUBLIC_ENDPOINTS`, so tile URLs are readable without a login by anyone who guesses the path.

**Auth.** Two interchangeable gates, both landing on `session['authed']` (checked by the `_require_login` before-request hook against `_PUBLIC_ENDPOINTS` in `routes.py`): (1) **Okta SSO** (preferred) — when `OKTA_ISSUER`/`OKTA_CLIENT_ID`/`OKTA_CLIENT_SECRET` are set, `app/auth.py` registers an OIDC client via discovery; `/login` bounces to Okta, `/authorize` exchanges the code and establishes the session, `/logout` does RP-initiated logout (to `OKTA_LOGOUT_REDIRECT_URI`, defaulting to the app's own `/logged-out` confirmation page). Access (to **view**) is gated by **Okta app assignment** — only users assigned to the Okta app can complete a login. (2) **`APP_PASSWORD`** — a single shared password (fallback when Okta isn't configured; grants admin). Unset+no-Okta → the app is open (dev convenience). `_auth_required()` = Okta-or-password configured. The remote agent is exempt either way — it authenticates with `X-Agent-Token` matching `AGENT_TOKEN`.

**Admin vs viewer (two-tier access).** Everyone who logs in can **view**; **edit** rights are gated on membership in the directory admin group (`ADMIN_GROUP`, default `Network Monitor Admins`). Membership comes from the Okta **`groups` claim** — the org *default* authorization server does NOT release groups (no groups claim/scope in its discovery), so the claim must be **configured on the Okta app** (ID token and/or userinfo; `authorize()` reads `token['userinfo']` and falls back to a `userinfo()` fetch if the claim isn't on the ID token). `_is_admin_from_claims` tests membership → `session['is_admin']`; password-mode logins are always admin. The **security boundary is server-side**: a second before-request hook `_require_admin` (after `_require_login`) lets a non-admin (viewer) reach only safe GETs — **blocking every mutating request and the user-activity trail** (`_VIEWER_BLOCKED = {user_activity}`, `_VIEWER_ALLOWED_WRITES = {export_xlsx}` for the read-only xlsx build) with a 403. `is_admin()` = open-mode-true-else-`session['is_admin']`; `index` passes it to the template, which injects `window.IS_ADMIN`. The frontend hides every edit affordance for viewers (Check Now, Edit Map, Add/Edit/Delete device, pause/resume, mark/schedule/edit/combine/delete event, Settings, Download agent, site add/edit, notes save→read-only, the decommission-undo popup, the User Activity tab) and shows a "View only" badge — but that's cosmetic; the 403s are the real gate.

**Key API routes** (`app/routes.py`, blueprint `main`; most take `?site=<key>`):
- `/api/topology` — switches + devices with status + position (from the in-memory caches; no per-poll DB read) (+ `pending_delete` / `monitoring_stale` for the site).
- `/api/devices/<ip>/history`, `/api/devices/<ip>/position` (POST), `/api/devices/<ip>/geo-position` (POST — lat/lng, used by Edit Map over an aerial basemap), `/api/devices/<ip>/note` (GET/PUT), `/api/devices/<ip>/enabled` (POST — pause/resume monitoring).
- `/api/basemap` (GET — tile source + georeferencing + visible window + saved default opening view for the site, `{}` if it has none), `/api/basemap/view` (PUT — refine or `{reset:true}` the visible area; admin-only), and `/api/basemap/open-view` (PUT — save/`{reset:true}` the default opening pan+zoom everyone lands on, per `layout` desktop/mobile; admin-only). See Aerial basemap above.
- `/api/devices/<ip>/log` — one device's offline/unknown/paused intervals (+ site app-downtime); `/api/devices/<ip>/tree-log` — a switch **and all devices downstream of it** (recursive), for the switch-log "this switch / connected devices" filters.
- `/api/log` — the site-wide chronological activity log (offline/maintenance/unknown/paused/app-downtime events). `/api/export/xlsx` (POST) — build an auto-fit Excel file from posted rows (openpyxl).
- `/api/user-activity` (GET) — the current location's audit trail (see the audit-trail section).
- `/api/events` (GET grouped Upcoming/Present/Past, POST create with optional pause), `/api/events/<group_id>` (PATCH times/description, DELETE — resumes devices if a linked pause is active). `/api/devices/<ip>/maintenance` (POST — quick per-outage tag, takes a `category`); `/api/maintenance/<id>` (PATCH / DELETE).
- `/api/devices/<ip>` (DELETE) / (PUT) — remove / edit a node. `/api/devices/add` & `/api/switches/add` (POST) — write to `nodes` via `db.add_node`, then `_reload_config`.
- `/api/sites` (GET via config / POST add), `/api/sites/<key>` (PATCH rename / DELETE = schedule soft-delete), `/api/sites/<key>/undo-delete` (POST).
- `/api/scheduled-pauses` (GET list / POST create — times entered Eastern, stored UTC; a pause must start **≥8h ahead**, `SCHEDULED_PAUSE_MIN_LEAD`, so the slow watchdog can catch it), `/api/scheduled-pauses/<id>` (DELETE = cancel, resuming devices if active). Applied by the watchdog thread's sweep; create/cancel call `db.refresh_open_pauses()` + `monitor.wake_watchdog()`.
- `/api/check-now` (POST) — requests an immediate agent check. Body `{ip}` → a **targeted** check of just that device (the single-device panel button); no body → a **full** sweep (the header button). Both set an in-memory per-site flag (`db.request_check(site, ips=)`) the agent consumes on its next `/api/agent/targets` poll; `agent/targets` returns `check_requested` plus `check_ips` (empty = full sweep, non-empty = ping only those IPs). A full request supersedes a pending targeted set for the site. **The agent must be redeployed to honor `check_ips`** — older agents ignore the field and fall back to a full sweep on `check_requested` (still correct, just not targeted). The targeted sweep posts a **partial** report (only that device), which `process_results` handles fine.
- `/api/agent/targets` (GET) & `/api/agent/report` (POST) — the agent's pull/push endpoints (token-authed; support `?site=all`).
- `/api/stats`, `/api/settings` (GET/PUT — the in-app Settings panel; see App settings below), `/login`, `/auth/callback` (Okta), `/logout`.

## Environment variables

Core: `DATABASE_URL` (Postgres; unset → SQLite), `SECRET_KEY` (session signing — **set in prod**, else logins/OAuth break across restarts), `AGENT_TOKEN` / `AGENT_TOKEN_<KEY>` (agent auth; open+warns if unset), `SLACK_WEBHOOK_URL` (default/app-wide channel) + `SLACK_WEBHOOK_URL_<KEY>` (per-location channel, e.g. `SLACK_WEBHOOK_URL_LOCATION_B`) / `POLLING_INTERVAL_MINUTES` (override `settings.yaml`), `DOWN_CONFIRM_CHECKS` (override the confirm-down count), `ENABLE_LOCAL_PING=1` (run the in-process pinger), `ENABLE_WATCHDOG` (default on; agent-silence + DB-unwritable Slack alerts + boundary-gated scheduled-pause sweep) + `WATCHDOG_STALE_MINUTES` (default 30) / `WATCHDOG_CHECK_SECONDS` (base tick, default **28800 = 8h**) / `WATCHDOG_NEAR_PAUSE_SECONDS` (tightened tick when a pause boundary is within the base window, default **1800 = 30min**) / `DB_WRITE_FAIL_ALERT_THRESHOLD` (default 3; consecutive transition-write failures before the DB-unwritable Slack alert fires), `APP_BASE_URL` (public app URL, e.g. `https://location-a.example.edu`; when set, each device in a Slack outage alert deep-links to its view page via `?device=<Device ID>&site=<key>` — the link is keyed by the stable **Device ID** (`name`), not the mutable IP, so it survives an IP change; the frontend resolves `?device=` by Device ID, falling back to IP for old links; unset → alerts show the plain hostname/IP with no link), `DEMO_MODE=1` (see Demo mode below).

**Note on the env-overridable tuning knobs.** `DOWN_CONFIRM_CHECKS`, `WATCHDOG_STALE_MINUTES` (and the frequent-outage window, ping count/timeout, reminder hours, alert-on-recovery) are now the **defaults** for the in-DB **app settings** (see below), not hard overrides — the settings panel wins once a value is saved, falling back to the env var, falling back to the built-in default.

## App settings (the in-app Settings panel)

The hamburger menu's **Settings** modal edits eight DB-backed tuning knobs that apply **app-wide** (across every location) and take effect live. They live in `app_flags` as `setting:<key>` and are cached in memory (`db._SETTINGS_SPEC` / `load_app_settings` / `get_setting` / `set_app_settings`, guarded by `_rt_lock`, seeded once at startup, no per-read DB hit). Each spec entry is `(default, min, max, env_var)` — `get_setting` resolves **saved value → env var → default** and every write is validated/clamped to `[min,max]`. The knobs: `outage_window_days`, `frequent_min_outages` (frequent-outage detection), `down_confirm_checks`, `ping_count`, `ping_timeout` (ping/down detection — the last two are sent to the agent in `/api/agent/targets`'s `polling` block), `watchdog_stale_minutes`, `reminder_hours`, `alert_on_recovery` (alerts). Read sites: `get_outage_counts`/`_frequent_set` (routes), `_monitoring_stale_minutes`, `agent_targets`, `monitor.check_agent_silence`/`process_results`/reminder, `notifier._build_payload` (recovery gate). Routes: `GET/PUT /api/settings` (`PUT` clamps, `invalidate_outage_cache()` + `monitor.wake_watchdog()`, audited "Changed app settings"). Frontend: `#settings-overlay` modal wired in `map.js` (fetch on open, PUT on save, then `fetchAndRender(true)`).

## Demo mode (`DEMO_MODE=1`)

A **display-only** abstraction layer for recording a public-shareable demo video — it does **not** change auth, mutations, routing, or the API (the real device `ip` stays every lookup/routing key). The site itself is never meant to be public; demo mode only sanitizes what's *on screen*. Split across two layers:
- **Server (routes.py `_demo_mode()` + `index`):** app title → "Network Monitor"; location names → "Location A/B/…" (the frontend reads site names from the DOM, so overriding them in the `index` template is enough); the User Activity tab is omitted; a `window.DEMO` flag is injected before `map.js`.
- **Aerial basemap:** forced off, including its toggle button (`updateBasemapChrome`), since the photo would identify the site outright.
- **Client (map.js `DEMO` + `demoName`/`demoId`):** each device gets a **stable** number from its sorted-by-IP position (`_buildDemoMap`, cache-keyed on switch/device counts) so it reads as the same "Switch N"/"Device N" across polls; `displayName` returns the demo label; Device IDs → "device-N-id"; IP rows/labels are hidden (map `sw-ip`, detail panel, tooltip); per-device notes are hidden (and `loadNote` skipped); event free-text titles/descriptions fall back to the generic **category** name (`evTitle`/`evHasTitle`), and the mark/edit-event prefills are blanked. The site-wide log's server-supplied names are remapped by IP to the demo label in `entryText`. **Known gap:** the Edit-Device modal still prefills real name/IP/location (kept functional for real edits; the demoer controls whether they open it).

Auth gate: `APP_PASSWORD` (shared-password fallback; open if unset), `ADMIN_PASSWORD` (extra gate to delete a location; deletion disabled if unset), `ADMIN_GROUP` (directory group granting edit/admin rights, default `Network Monitor Admins`). Okta SSO: `OKTA_ISSUER` (`https://sso.example.com` at the org), `OKTA_CLIENT_ID`, `OKTA_CLIENT_SECRET`, `OKTA_REDIRECT_URI` (`…/auth/callback`), `OKTA_LOGOUT_REDIRECT_URI` (defaults to the app's `/logged-out` page — must be a registered Okta "Sign-out redirect URI"), `OKTA_SCOPES` (default `openid email profile`), `SESSION_COOKIE_SECURE` (defaults on with SSO), `AUTH_DEBUG=1` (show token-exchange errors). Login (view) is gated by Okta app assignment; **admin (edit) rights need the `groups` claim configured on the Okta app** (see the Admin-vs-viewer note above). See `README.md` for the full table and Neon/Heroku setup.

## Things to know before editing

- **`_reload_config` (after add/delete) only restarts the scheduler when `ENABLE_LOCAL_PING=1`.** On Heroku the scheduler is off, so no restart happens — the remote agent picks up list changes on its next `/api/agent/targets` poll (which reads `app.config['DEVICES']` live). The `_scheduler_thread`/`_stop_event` module globals in `monitor.py` mean only one scheduler runs at a time.
- **`config/devices.yaml` is a seed, not a relic — don't delete it.** `load_yaml` does a bare `open()`, so a missing file crashes `create_app()` on any empty DB (fresh local SQLite, new Neon project, DB reset). It's also the only git-versioned backup of the ~110-device list.
- **The aerial basemap has two coordinate spaces and `projectNodes` mutates x/y in place.** Anything that turns the photo off must **refetch** the topology, not re-render the cached copy (see `togglePhoto`), or an Edit Map save will write image pixels into the logical layout. Likewise, geometry sized in screen pixels (`SW_W/2`, marker sizes) must be divided by the zoom scale before being compared with world-space deltas — `swLinkPoints` is the precedent. See Aerial basemap above.
- **Regenerating imagery means bumping the tile version.** Tiles are served `immutable` for a year keyed on the `v<n>` path segment; rebuilding in place at the same version leaves stale tiles in every browser cache. `maps/build_tiles.py --version <n+1>`, then update `basemaps.yaml`.
- **Timestamps are stored UTC** and converted to local in the browser by appending `'Z'`. See the timestamp caveat above; keep the convention for new time fields.
- **`debug: true` in settings.yaml would break the scheduler** under Flask's reloader (double process/thread). Leave debug off when `ENABLE_LOCAL_PING=1`.
- AP-to-switch (and switch-to-uplink) association is by switch **`name`**, but **storage/state reads are still keyed by `ip`** — don't conflate the two. **Migration in progress → a stable surrogate `node_id` as the identity, away from IP** (because IPs change). Progress so far:
  - **Interface (done):** Slack outage-alert deep links are keyed by Device ID (`?device=<name>`), and the frontend resolves `?device=` by Device ID with an IP fallback. The **per-device API accepts a Device ID *or* an IP** — a `before_request` hook (`_resolve_device_ref`) rewrites the `<ip>` view-arg of every `/api/devices/<ip>/…` route via `_resolve_ref` (Device ID → current IP; an IP passes through unchanged), and `/api/check-now` takes `{device:<id>}` or `{ip}`; the frontend sends the Device ID (`devRef(node)` = encoded `name`). When adding a per-device route it gets Device-ID resolution automatically via the hook — keep using `ip` inside the view.
  - **Storage foundation (Phase 3a, done):** `nodes.node_id` is a **stable surrogate integer** (assigned by `add_node`/`seed_nodes_from_yaml`, never changes — survives both IP *and* Device-ID renames). Every per-device table (`ping_history`, `device_states`, `device_positions`/`_mobile`/`_geo`, `device_notes`, `pause_periods`, `maintenance_windows` — the `_PERDEVICE_TABLES` tuple) carries a **backfilled `node_id`** (migration `_migrate_add_node_id`), and every write path **dual-writes** it alongside `device_ip` via `_nid(ip)`.
  - **Cache flip (Phase 3b, done):** the in-memory runtime caches (`_states`, `_positions`/`_mobile`/`_geo`, `_persisted_status`) are now **keyed by `node_id`**, loaded that way in `load_runtime_caches` and updated by `record_ping`/`set_position`/etc. Two in-memory maps maintained together — `_ip_to_nid` / `_nid_to_ip` (via `_set_ip_nid`/`_forget_ip`/`_ip_of`) — translate at the **ip-based public accessor boundary** (`get_all_states`/`get_positions`/`get_geo_positions`/`get_overdue_down`), so callers/routes are unchanged. **Consequence:** an IP change no longer re-keys the caches (node_id is stable), and `update_node` now migrates `device_ip` across **all** `_PERDEVICE_TABLES` (previously it skipped `maintenance_windows` — a latent bug). **`device_ip` is still fully maintained as a dual-written safety net, and the DB read queries still key by `device_ip`** — that read-query flip + dropping the `device_ip` net is the final phase (3c); it's deferred because with `device_ip` maintained it's functionally neutral and pure risk on a DB that can't be tested from dev. The events subsystem's `device_ips` and the agent protocol still use IP. So the runtime source of truth is node_id-keyed now, but nothing yet *depends* on node_id for durable reads — still reversible.
- **Ping by DNS, keyed by IP.** Each node has an optional `nodes.hostname` (DNS name). `/api/agent/targets` sends a `host` field per device = `hostname or ip`; the agent pings `host` but **reports results under `ip`**, so the IP stays the identity/routing key for every per-device table and nothing downstream changes. A node with no hostname pings by IP (the cameras/panel). Old agents ignore `host` and ping the IP (graceful). Hostnames are edited per-device via the Edit Device modal's **DNS Hostname** field (`db.set_node_hostname`/`update_node`). The initial fleet-wide DNS load (all locations) was done once via a throwaway `scripts/import_dns.py` that resolved sheet rows to nodes against the live DB and set `hostname`; that script + its CSV were deleted after the run (recover from git history if a re-import is ever needed). UI: IPs are hidden on the map's switch labels and the sidebar rows; IP + DNS show on the single-device panel. Demo mode hides the DNS row (org-identifying).
- **Intermapper link.** Each node has a `nodes.intermapper_url` — its page on the org's Intermapper monitoring site. It's a **required field when creating** a device/switch (the Add form's `f-intermapper` input, `required`; enforced again in `add_device`/`add_switch` → 400 if empty; on edit it's kept when the key is omitted and can't be blanked). The single-device panel shows a **"View device in Intermapper ↗"** link (`node.intermapper_url`, opens a new tab; hidden in demo mode). Threaded through `_node_entry`/`add_node`/`update_node` and the topology responses (`_device_response`/`_switch_response`) exactly like `hostname`. The initial fleet-wide backfill was a throwaway `scripts/import_intermapper.py` + `scripts/intermapper_links.csv` (match by Device ID against the live DB); delete both after running, like the DNS import.
- **Single web process is assumed.** The in-memory runtime caches (device status, positions, watermark, check-flag — see the in-memory-state section) only work because gunicorn runs `1 worker × 4 threads` (shared memory, RLock-guarded). Scaling `web` past 1 dyno or raising `--workers` would give each process its own diverging cache — you'd need a shared store (or to revert the caches to DB-backed) first. `min_size=0` on the pool + these caches are what let Neon's compute auto-suspend during quiet periods.
- **There is no background scheduler in production** (the daemon thread is off without `ENABLE_LOCAL_PING`). Time-based work runs as a **lazy sweep** on frequent request paths: `purge_due_site_deletions()` (the 24h location delete) fires from `/api/topology` and `/api/agent/report`. This is reliable only while the app gets traffic — fine given the agent reports every ~2 min, but don't assume anything fires on a fully idle app. For a hard guarantee, add a Heroku Scheduler cron.
- **`Authlib` and `openpyxl` are imported lazily / guarded** so offline dev without SSO still runs. `app/auth.py` degrades gracefully (`okta_enabled()` returns False) if Authlib is missing.
- **Frontend `[hidden]` gotcha:** several base classes set `display` (`.filter-group`, `.btn`, `.form-row`, `.dot`), which overrides the HTML `hidden` attribute. When you rely on toggling `.hidden` in JS, add a matching `.<class>[hidden] { display: none }` rule (there are several precedents in `style.css`).
